# Rings 1.2.0 — Tree Web Chat, a Durable Turn Queue and Safe Stop

Rings v1.2.0 / Phase 11A. Migrations `0001`–`0020`. Previous tags `v1.0.0`, `v1.1.0` and `v1.1.1`
are unchanged.

## What this release is

The browser becomes the preferred daily way to talk to Tree. The conversation runtime does not
change: it is still one `ConversationService`, still a closed capability registry, still a model
with no tools. What changes is who can reach it and how honestly it can narrate itself.

```text
browser ──► /chat + /api/chat/* ──► durable request queue ──► ConversationService
                                                                    │
                                            existing capabilities, confirmations, approvals
```

## Added

**Tree Web Chat.** `/chat` serves a self-contained page (local HTML, CSS and JavaScript — no
framework, no build step, no CDN). It shows conversation history, lets you switch threads and start
a new one, keeps a multiline composer usable while Tree is working, and displays Tree's activity as
product language rather than as internals. The composer is safe with a Chinese IME: Enter sends,
Shift+Enter breaks the line, and Enter during candidate selection never submits.

**A durable turn queue.** A submitted message is stored before anything runs, so it survives a page
reload and a process restart. One thread runs one request at a time; a retried POST is the same
request because the browser's `client_request_id` is part of a unique key. Extra messages queue
behind the active one and are shown as 排队中, each as its own turn.

**Restart recovery that never replays.** A request left `PROCESSING` by a crash is resolved from
its linked turn. Terminal turns are mirrored; a turn parked waiting for your confirmation is
accepted as finished; anything else becomes `INTERRUPTED`. Only work that had not started is
resumed, because only there is it provable that nothing happened.

**Safe Stop.** Stop is offered while a request is queued or while Tree is still understanding it —
before any mutation. After that, the server refuses with `CANNOT_CANCEL_SAFELY` and says so in
words. A stop that arrives during a model call abandons that call's answer rather than waiting to
apply it, so nothing is written. Stop never claims to have undone an external effect, and an SMTP
`UNKNOWN` stays `UNKNOWN`.

**An ephemeral activity stream.** Server-sent events carry coarse stage changes and safe
notifications. Subscriber queues are bounded; a client that falls behind is told to resynchronise
instead of being buffered for. The stream is not authoritative — a reload always refetches a
durable snapshot — so a reconnect, a second tab or a restarted process cannot produce a wrong
screen.

**Confirmation cards.** Structured cards replace "remember the vocabulary" for the four decisions
that already existed:

* **邮件发送预览** — the exact message, built from the immutable `ActionRequest` payload, with
  `确认发送` / `取消`;
* **周计划** — the proposal's blocks with task titles and durations, with `应用计划` / `取消`;
* **固定安排** — the whole weekly-schedule group, with `保存固定安排` / `取消`;
* **长期信息** — the proposed key, value and the sentence it came from, with `确认记住` / `不要记`.

Each card carries an `expected_revision`. If the durable state moved on, the click is refused with
`409 STALE_CONFIRMATION`, nothing is applied, approved or sent, and the page reloads the truth. The
buttons never call a model: they settle the exact target through the same deterministic controllers
the terminal phrases use, and the exact `ApprovalChallenge` value never reaches JavaScript.

**`rings --web`.** Opens the configured `/chat` URL with the standard library's `webbrowser` when
the control plane is running, and otherwise prints how to start it — no daemon is started silently,
no shell command is run and no browser is automated. `rings` on its own is unchanged.

**Operational coverage.** `pw integrity check` now verifies the queue read-only (status, timestamps,
thread and turn correlation, one active request per thread, no live terminal row), and a queued
request is part of a backup: it comes back from a restored archive still claimable, while a
`PROCESSING` row comes back as durable intent that the next start resolves rather than replays.

## Changed

* Conversation history read with a limit no longer returns messages written in the same instant in
  reverse order.

## Security and privacy

Nothing in the v1 boundary moved. The browser has no domain, repository or executor access; there
is no shell, filesystem, browser or generic HTTP capability anywhere near it; the model still has
no tools and cannot create an approval. The chat surface reuses the existing session, CSRF and
private-client rules — there is no anonymous LAN path, no wildcard CORS and no new credential. All
user, model, mail and contact text reaches the page as text: the shell uses `textContent` and has no
markup assignment, no `eval` and no remote asset. Progress never contains a prompt, a provider
response or a reasoning step, and server logs carry ids, statuses and stages — never message text,
mail bodies, fact values or tokens.

## Non-executing by construction

The browser is not an executor and cannot become one by accident. There is no generic
`/execute`, `/tool`, `/action`, `/approval`, `/sql` or `/shell` route; the production executor set is
unchanged (`mail.send` and `ehall.submit-certificate`, and the second is reachable only through its
typed pipeline). A card click settles a reviewed decision that already exists; it never creates a
new capability, and no browser code decides whether something is authorized.

## Known limitations

This is a truthful list, not a roadmap promise.

* **Mail account setup is still configuration work.** The web UI can say that no sending account is
  configured; it does not configure one. There is no SMTP/IMAP wizard, no OAuth flow and no
  password UI in this release.
* **Attachments are not available**, in the terminal or in the browser.
* **Cc, Bcc and multiple recipients remain limited** to what the existing compose and review paths
  support.
* **Scheduled mail is not available.**
* **Complex recurrence is not available**: weekly, same-day, non-overnight rules only.
* **Conversational eHall is not available.** The typed certificate pipeline is unchanged and still
  begins at `pw`.
* **Voice is not available.**
* **There is no remote or cloud-hosted UI.** The web chat is a same-LAN control plane: it binds
  loopback or the local network, and it does not claim `Secure` cookies because it is plain HTTP.
* **Web chat uses the existing local/trusted-LAN security model.** Pairing, sessions and CSRF are
  the same mechanisms v1.1 shipped; a network you do not trust is still a network you should not
  pair.
* **MCP remains bounded and local**, with no approval and no execution.
* **The LAN control plane is a trusted network by assumption.** The exact review boundary above is
  what keeps an effect honest, and exactly one human approval is still required before it.
* **Stop cannot undo an external execution that has already started.** After the boundary the
  answer is `CANNOT_CANCEL_SAFELY`, and an SMTP result that is `UNKNOWN` stays `UNKNOWN`: it is
  never blind-retried, and it needs the existing reconciliation path.
* **A confirmation card is not an editor.** To change what a card is about, say the change in the
  composer; the old card goes stale and a new one appears.

## Exactly-once, honestly

An external effect still has exactly one path: `ActionRequest` → exact immutable fingerprint →
explicit human confirmation → `Approval` → `ExecutionRun`. A card click is a human confirmation,
not an automation: it consumes exactly one approval and can never produce a second execution. A
retried POST is one request, a double-click is one settlement, and a stale card can send nothing.
The queue itself is at-least-once in the only sense that matters — queued work is retried by
restart, while work that had already started is resolved rather than replayed. Everything a
conversation does before that boundary is non-executing: a model answer that cannot be validated
changes nothing. The surface stays a trusted LAN control plane: exactly-once external effects still
require one explicit human approval, and the browser is only a way to give it.

## Migrations

`0001`–`0020`. `0020_conversation_requests.sql` adds the accepted-input queue, its three indexes
(idempotency, per-thread order, one active request per thread) and the nullable
`conversation_turns.request_id` correlation with its partial unique index. `0001`–`0019` are
unchanged, as are the three existing tags.

## Upgrading

```bash
uv run assistantd
```

applies `0020` forward. A 1.1.x runtime keeps its conversations, facts, mail, plans and sessions; a
host without a `[model]` section keeps the v1.1 control plane and simply has no `/chat` routes.

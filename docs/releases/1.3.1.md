# Rings 1.3.1 — Patch Release: Pairing That Sticks, and an Honest Browser Probe

Rings 1.3.1 fixes two things in the 1.3.0 surface that a user meets immediately. No capability was
added, no migration was added, and the safety boundary is unchanged.

## Fixed

- **A paired browser stays paired across a browser restart.** The session and CSRF cookies were set
  without `Max-Age`, which makes a browser drop them when it closes — while the server-side session
  stayed valid for 30 days. The visible effect was being asked to pair again every time you opened
  `/chat` or `/settings`, and a `pw mobile sessions` list that kept growing. Both cookies now carry
  the session's own 30-day lifetime, so the cookie and the session row finally agree. `HttpOnly`
  (session), `SameSite=Strict` and the deliberate absence of `Secure` on LAN HTTP are unchanged, and
  the pairing code itself is still single-use and short-lived.
- **`pw ehall status` and `pw doctor` report the browser build Playwright will actually launch.**
  The old probe asked "is any `chromium-*` directory in the cache?", which is true after a
  dependency bump that left an older build behind — so the status said
  `Chromium runtime: available` and `pw ehall login` then failed with "Chromium is not available".
  The probe now reads Playwright's own `browsers.json`, requires the expected build directory *and*
  its executable, and names the build in the answer:

  ```text
  Chromium runtime    │ available (chromium-1243)
  Chromium runtime    │ missing (expected chromium-1243; run `uv run playwright install chromium`)
  ```

  An interrupted download (a directory with no binary) is reported as missing too. Nothing in
  either command downloads anything or starts a browser.

## Upgrade

Nothing to do beyond upgrading the package: this release adds no migration, so the schema is still
the `0023` set from 1.3.0, and a backup taken with 1.3.0 restores unchanged.

## Known limitations

Everything v1.3.0 documented still holds, including the ones this patch touches:

- **Cookie persistence is the browser's promise, not ours.** If a browser is configured to clear
  cookies on exit, or an ephemeral profile (a private window, some in-editor browsers) is used,
  there is nothing left to present and pairing is required again. Cookies are also scoped to a
  host, so `127.0.0.1:8765` and `localhost:8765` are two different "browsers"; use one of them
  consistently.
- **The Chromium probe is still a probe.** It checks that the expected build and its executable
  exist; it never launches a browser to prove it, because a status command that starts a browser is
  not a status command.
- **One eHall capability.** Only the certificate application service exists; dropping a course,
  withdrawing or cancelling an application and every other university form are absent from the code.
- **No form autofill.** Every submitted certificate value must appear in your own message.
- **The web surfaces are a trusted LAN control plane.** No public hostname, no TLS, no proxy trust
  and no cloud relay.
- **Playbooks remain non-executing.** A playbook cannot be run, parameterized or turned into an
  action.

## The safety boundary, restated

This release changes cookie lifetimes and one read-only probe; it does not touch the part that
decides what may happen to the world. An external effect still needs an exact `ActionRequest`, a
human `Approval` bound to its fingerprint and one `ExecutionRun`: sending needs `确认发送`,
submitting a certificate needs `确认提交`, a generic `可以` does neither, an ambiguous result is
`UNKNOWN` and is never retried automatically, and `exactly-once` is either achieved or reported as
an honest unknown. Mobile may approve but never execute.

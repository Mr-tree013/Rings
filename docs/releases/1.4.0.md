# Rings 1.4.0 — One Command to Start

Rings 1.4.0 is about the first ten seconds of using it. Starting the product took four manual steps
in three places — a second terminal, a hand-pasted pairing code, two credential exports and a
separate eHall login — and two of them expired. Now it is one command, and optionally none after
logon. See ADR-0046 for the decisions and `docs/specs/0002-one-command-startup.md` for the design.

## What is new

```bash
uv run rings up          # 起服务（或复用已在跑的）+ 自动配对 + 打开 /chat，并打印状态
uv run rings down        # 优雅停止；进行中的对话会被标为 interrupted，绝不重放
uv run rings autostart install   # 可选：Windows 登录时自动常驻，一个文件，删掉即撤销
```

`rings up` prints a status block that says what is actually true:

```text
daemon        已启动（pid 988974，1.4.0）
web           http://127.0.0.1:8765/chat
配对          本次已自动配对
凭据          从 secrets.env 读到 GROWING_ASSISTANT_MAIL_SMAIL_PASSWORD（新载入 1 项）
邮件          smail：1/1 个凭据就位，已存 6 封
eHall         profile 已存在；只有实时检查才知道登录是否仍然有效
```

- **Automatic pairing, without weakening the code.** `rings up` mints one pairing token — the same
  one-time, 600-second, hash-only value `pw mobile pair` prints — and opens
  `http://127.0.0.1:<port>/chat#pair=<token>`. The fragment never reaches the server, the page
  strips it with `replaceState` before anything else, and the token is redeemed through the
  **existing** `/api/pair` route only when this browser is not already paired. No new route, no
  query string, no second session for a browser that already has one.
- **A user-owned secrets file.** `~/.config/growing-assistant/secrets.env` (mode 0600 or it is
  refused) holds the mail app passwords and the provider key. The environment still wins, so a
  one-off `export` overrides it; the vocabulary is closed, so the file cannot become a general
  secret store; and nothing in the product ever writes it, prints a value from it or logs one.
- **Detached by default.** The daemon no longer dies with the terminal that started it. Its output
  goes to `<runtime>/assistantd.log` (0600, rotated once at 5 MB per start), and `--foreground`
  remains for watching it live.
- **Honest readiness and honest stopping.** `rings up` waits (bounded) for the lock *and* for the
  control plane to answer, and on timeout prints the log path and its last lines instead of claiming
  success. `rings down` sends `SIGTERM` to the process that actually holds the lock and waits for it
  to let go; stopping a stopped daemon is not an error.

## Code complete vs real account not configured

This release is code complete and tested against a real daemon subprocess (start → reuse → stop) and
a real Chromium (fragment pairing); the secrets-file paths are tested without a real host file. The
machine that built it has a configured mail account and an eHall profile, and **no** real message was
sent and **no** certificate was submitted while building this release.

## Known limitations

- **The web surfaces are a trusted LAN control plane.** No public hostname, no TLS, no proxy trust,
  no cloud relay; the pairing code is still short-lived and single-use, and sessions last 30 days.
- **Cookie persistence is the browser's promise, not ours.** A browser configured to clear cookies on
  exit, or an ephemeral profile, will still need pairing again; cookies are also host-scoped, so use
  one address (`127.0.0.1:<port>`) consistently.
- **eHall SSO stays manual.** `pw ehall login` opens a headed browser and the person logs in; Rings
  never asks for or stores a university password, and `rings up` can only report whether a profile
  exists, never whether the session is still valid.
- **The always-on option costs something.** A resident daemon means the mail pipeline analyses new
  mail while nobody is watching, and `Vmmem` keeps the WSL VM alive; `rings down` is the switch for
  both.
- **Autostart is Windows-specific.** It writes one `.cmd` in the per-user Startup folder; other
  hosts keep the manual command.
- **One eHall capability.** Only the certificate application service exists; no autofill, no arbitrary
  browser action, no destructive university workflow.
- **Playbooks remain non-executing.** A playbook cannot be run, parameterized or turned into an
  action.

## The safety boundary, unchanged

An external effect still needs an exact `ActionRequest`, one human `Approval` bound to its
fingerprint and one `ExecutionRun`: sending needs `确认发送`, submitting a certificate needs
`确认提交`, a generic `可以` does neither, and an ambiguous result is `UNKNOWN` and never retried
automatically — `exactly-once`, or an honest unknown. Mobile may approve but never execute. This
release changed how Rings *starts*; it did not widen what Rings may *do*.

## Upgrade

No migration is added: the schema is still the `0023` set from 1.3.0 and a 1.3.x backup restores
unchanged. One manual step is optional and one-time: create
`~/.config/growing-assistant/secrets.env` (0600) if you would rather not export credentials in every
shell.

# Rings 1.1.1 — terminal editing and confirmation correctness

**Released:** 2026-09-21 · **Reference environment:** Linux / WSL + Python 3.13 · **Migrations:**
`0001`–`0019` (unchanged)

Rings 1.1.1 is a focused hotfix. It adds no product capability: it fixes two defects a real user
hit in v1.1.0 — editing a line in `rings`, and revising a pending local confirmation.

## What is fixed

### Editing a line in the terminal, in Chinese or otherwise

`rings` now edits input with a real terminal line editor (`prompt_toolkit`) whenever stdin and
stdout are actual terminals. Left/Right move the cursor, Home/End work, Backspace and Delete remove
one *character* — so deleting a Chinese character no longer leaves an incomplete UTF-8 sequence
behind — and CJK display width comes from the editor. Up/Down walk the session's own history.

Before this release the interactive path read a whole line from the terminal as bytes. Arrow keys
were therefore ordinary text: `^[[D` and `^[[C` were submitted to the conversation, and a Chinese
character deleted a byte at a time could no longer be decoded at all, which is why Tree answered
"刚才的输入包含无法识别的终端字符". That message was the strict decoder doing its job on input that
no longer meant anything; what was missing was a real editor in front of it.

- Arrow keys are editing commands and can never reach a conversation turn.
- Home/End/Backspace/Delete, bracketed paste and mixed Chinese/ASCII editing all work.
- Editing history is kept **in memory only**. Nothing is written to `~/.history`, `~/.rings_history`
  or any other file — a prompt may contain private data. The durable record of a conversation is
  still the conversation itself.
- Ctrl-C discards the unfinished line and returns to `You >`; Ctrl-D on an empty prompt exits
  cleanly; `/exit` is unchanged.
- After the editor returns, the text is validated once more: no NUL, no lone surrogate, no raw ANSI
  control sequence, no unintended control character. Ordinary text — tabs, Chinese punctuation,
  quotes, angle brackets, `@`, emoji — passes through unchanged. A rejected line produces no turn,
  no model call and no mutation, and the session stays open.
- **Piped and scripted input is unchanged**: `pw chat` with a pipe keeps the strict decoder and the
  fail-closed behaviour of v1.1.0, so existing scripts and tests behave exactly as before.

### Revising a pending confirmation

When a proposal was revised before it was confirmed, the runtime used to keep both proposals live.
Confirming then applied the old one *and* the new one — the user's transcript shows a bare
`计算机系统基础（ICS）` rule being created as a side effect of a superseded question.

Now a pending local confirmation is a **group**: the set of operations one turn put in front of the
user, bounded by that turn. A revision of the same kind of proposal retires the group it replaces
(its operations become `REJECTED`, and its turn stops waiting), so:

- one `可以` settles exactly one group;
- a superseded group can never be applied afterwards;
- when two unrelated groups are waiting — a weekly schedule and a plan to apply, say — Tree asks
  which one instead of guessing, and applies neither;
- `取消` withdraws the outstanding questions without applying anything;
- external mail still requires its own explicit `确认发送`, a generic `可以` still never sends, and
  fact confirmation still requires its own words.

Confirming a group now reads as one answer: a single "已加入固定安排：" list, with rules that already
existed counted in one sentence ("其中 2 条已存在，没有重复添加。") instead of a paragraph per rule.

## Compatibility

- **No migration.** The schema stays at `0001`–`0019`; nothing is rewritten, and no status was
  added. A superseded group is expressed with the existing `REJECTED` result.
- The `pw` command surface, the daemon, the mobile control plane, MCP resources and the external
  action/approval boundary are unchanged.
- One runtime dependency was added: `prompt-toolkit`, used only as the interactive line-editing
  frontend (ADR-0040 §6). It is not imported by the non-interactive path.
- `v1.0.0` and `v1.1.0` remain published snapshots; `v1.1.1` is a fix, not a replacement.

## If you already have the duplicate rule

The hotfix prevents new duplicates; it deliberately does **not** touch your existing data. If
v1.1.0 already created the bare `计算机系统基础（ICS）` rule for you, retire it yourself — either by
asking Tree (`以后周二下午两点那门课没有 ICS 这个旧版本了` style phrasing, or by listing your
固定安排 first and then retiring the one you mean), or with `pw calendar recurring …` — and check
`我有哪些固定安排？` afterwards. Nothing in this release deletes or retires user data
automatically, at startup or in a migration.

## Known limitations

- **Attachments** are not supported in any mail flow.
- **One recipient per new letter**: no `Cc`, no `Bcc`, no multi-recipient compose.
- **No scheduled or delayed mail**, and no automatic sending of any kind.
- **Recurrence is weekly only**: no odd/even weeks, no every-N-weeks, no monthly or yearly rules, no
  holiday or exam-week exceptions.
- **Conversational eHall is unavailable**: the certificate pipeline stays an explicit `pw` approval
  flow.
- **No voice interface and no web chat**: the surfaces are the terminal, the trusted-LAN mobile
  page (view/approve only) and the local MCP server.
- **Linux / WSL is the reference runtime.** The project is developed and tested there.
- **Windows IME composition is the terminal's business.** Once the terminal commits Unicode text,
  Rings accepts it correctly; the application cannot and does not manage composition itself.

## Guarantees that did not change

- **exactly-once external effects, on demand**: one approved `ActionRequest` produces at most one
  `ExecutionRun`, and a restart never re-executes anything.
- **non-executing** local reasoning: a model answer that is unusable executes nothing.
- **trusted LAN only** for the mobile surface, with the same read-only-by-default boundaries.
- No credential, mail body, fact value or raw user input is logged.

# Rings 1.3.0 — Attention, Mail Settings, Planning 2.0 and a Bounded eHall Certificate

Rings 1.3.0 is the capability sprint. Four things a person asked for in v1.2 are now real, each
with the rule this project has kept from the beginning: nothing external happens without an exact
preview, the human's own phrase and a consumed approval. See ADR-0042 through ADR-0045 for the
decisions.

## What is new

- **A proactive inbox (`需要处理`).** Overdue and approaching deadlines, mail that asks for a reply,
  plans and confirmations waiting for you, unresolved external outcomes, reminders and observations
  are projected into one deterministic, deduplicated list on `/chat` and in the terminal. It is
  derived state: acknowledging or dismissing an item never completes a task, sends a letter or
  applies a plan.
- **Mail account settings (`/settings` → 邮箱).** Account metadata is managed from the browser
  through a managed overlay file, with read-only IMAP and SMTP connectivity tests that never send a
  message. Credentials stay environment-only: the browser stores a *reference*, never a password,
  and a change takes effect after `assistantd` restarts.
- **Planning 2.0.** Durable capacity preferences (planning day, daily minute budget, preferred and
  maximum block length), deterministic splitting of large tasks, and `plan.replan_week`, which
  proposes a replacement for the rest of the week. Applying a proposal is still your decision, and
  manual blocks are never replaced by the planner.
- **A conversational eHall certificate.** `ehall.status` reads the live certificate form, and
  `ehall.certificate.prepare` prepares one exact certificate application using the values you wrote
  and nothing else. The preview lists every field that would be submitted; only your own `确认提交`
  settles it; and one `确认提交` produces exactly one approval, exactly one execution run and exactly
  one click.

## Code complete vs real account not configured

This release is code complete and tested end to end against fakes and a fake certificate page. It is
**not** configured with any real external account on the machine that produced it:

- no real mailbox is configured, and no message was sent or received while this release was built;
- the eHall pipeline is disabled by default (`[ehall] enabled = false`), no university credential
  exists anywhere in this repository, and no real certificate was submitted.

`system.capabilities` — and `/settings` → 系统状态 — reports the truth for the host you are on:
`not_configured` until you configure it, `available` once you have, and never anything in between.
Screen text in this release is Chinese, matching the rest of the product surface.

## The safety boundary

- **The model prepares; it never submits.** The conversation vocabulary gained exactly two eHall
  operations. There is no `ehall.submit`, no `approval.create`, no `action.execute` and no
  `browser.*`, and the eHall executor is not reachable from the conversation path at all.
- **Preparation is not submission.** Preparing creates one immutable `ActionRequest` and shows a
  preview rendered from that payload. Until you confirm there are zero approvals, zero execution
  runs and zero keystrokes.
- **Generic acknowledgement never moves an external effect.** `可以`, `好`, `ok` and `继续` settle
  local proposals only. A letter needs `确认发送`; a certificate application needs `确认提交`; the two
  vocabularies are disjoint, and one sentence never settles two capabilities.
- **The same boundary in the browser.** A confirmation card settles exactly one durable target, by
  identity, with no model in the path, and a stale card submits nothing.
- **exactly-once, or honestly not.** An ambiguous external result is `UNKNOWN`, is never retried
  automatically, and blocks that action until a person looks.
- **Nine failure states are told apart.** Not configured, needs a login, connection failed,
  credential missing, unsupported capability, ambiguous reference, unknown external result, stale
  confirmation and cannot-cancel-safely each read differently, and no reply ever contains a
  traceback, a schema error or an internal identifier.

## Known limitations

- **One eHall capability.** Only the NJU certificate application service (`证明书申请`) exists.
  Dropping a course, withdrawing or cancelling an application, dorm checkout and every other
  university form are absent from the code, not merely discouraged by a prompt.
- **No form autofill.** Every submitted value must appear in your own message. There is no
  `ConfirmedFact`, mail, knowledge or model-memory autofill, and no plan to add one silently.
- **Manual login.** A headed browser (`pw ehall login`) is the only login path. Rings never asks for
  and never stores a university password, and it cannot tell whether a saved session is still valid
  without a live inspection.
- **Mail settings need a restart.** Account changes are written to a managed overlay and take effect
  after `assistantd` restarts; the settings page says so instead of implying otherwise.
- **The mobile and web surfaces are a trusted LAN control plane.** No public hostname, no TLS, no
  proxy trust and no cloud relay; they are not hardened for the open internet.
- **Playbooks remain non-executing.** A playbook cannot be run, parameterized or turned into an
  action; the Phase 7 blueprints are reference material only.

## Upgrade

`pw` migrates the runtime database forward automatically. This release adds migrations through
`0023`, so a v1.2 database keeps every mail review it had: migration 0023 widens one closed
constraint and copies every row across unchanged. `pw backup create` is unchanged, and a restored
archive carries the attention state, the planning capacity preferences, superseded plan blocks and
pending reviews — while never recreating an approval or an execution.

# growing-assistant 1.0.0 — Growing Personal Assistant v1.0

Released: 2026-09-26

## What v1.0 is

A **local-first Personal Operations System**. It runs on your machine, keeps its state in one SQLite
database plus the files that database references, and connects to the outside world only through
integrations you configure — and only, for anything that changes the world, after you approve one
exact action.

It is not an autonomous general-purpose agent. It has no shell, no filesystem control, no generic
browser and no generic HTTP client; the risky university errands do not exist in its capability set;
and nothing in it approves its own work.

## Major capabilities

| Area | What v1 does |
| --- | --- |
| Observe | Incremental IMAP receive-only mail; configured public HTTPS page watchers; hand-pasted or forwarded text (`pw ingest`) |
| Understand | Deterministic parsing and threading; model analysis through a provider-neutral port, producing candidates only; grounded answers over a local FTS5 index with exact citations |
| Commit & plan | Tasks, deadlines, calendar events, plan blocks, work sessions; deterministic weekly proposals you review and apply; durable reminders and rolling replans |
| Execute | Cases, immutable `ActionRequest`s, hash-bound single-use human approvals, `ExecutionRun` records; exactly two production capabilities — `mail.send` and the whitelisted eHall certificate pipeline |
| Review | Every action, approval and execution is durable history; `UNKNOWN` external results stay unresolved instead of being retried |
| Learn | Corrections → fact candidates → human-confirmed facts; successful runs → playbook candidates → dry-run replay → human promotion into a **non-executing** playbook |
| Interact | CLI (`pw`), a trusted-LAN mobile control plane, and a local stdio MCP server for VS Code |
| Operate | Read-only integrity audit, consistent `.gab` backups, staging-only restore, single-instance daemon, owner-only permissions |

## Safety model

1. **No external effect without a human approval bound to one exact fingerprint.** The approval is
   spent when execution begins; a changed payload invalidates it.
2. **The never-implemented capabilities are absent from the code**, not forbidden by a prompt:
   drop-course, withdrawal, dorm checkout, generic browser control, generic shell or filesystem or
   HTTP execution.
3. **Models propose; code and durable state decide.** Model output is validated against a closed
   schema and can only become a candidate, a draft or a proposal you explicitly apply.
4. **Ambiguity is preserved, never guessed.** An interrupted SMTP or eHall submission becomes
   `UNKNOWN` and stays visible instead of being retried into a duplicate effect.
5. **Recovery does not re-arm.** A restore invalidates outstanding challenges, approvals, pairing
   codes and mobile sessions, while keeping all history and every unresolved execution.
6. **The attention boundary is explicit:** an offline audit that never repairs, a backup whose
   contents are hashed, and a restore that only ever writes into a new, empty staging directory.

## Local-first architecture

Modular monolith, one asyncio daemon, explicit state machines, SQLite as the runtime authority.
Runtime state lives under `$XDG_DATA_HOME/growing-assistant/`; configuration under
`$XDG_CONFIG_HOME/growing-assistant/`; derived indexes under `$XDG_CACHE_HOME/`. Your documents stay
where they are — a vault that is unplugged is reported as offline, never as corruption, and derived
indexes are always rebuildable.

Two external authorities are deliberately *not* copied anywhere: your original documents and your
credentials. Credentials are environment-only, and they are not part of a backup.

## Supported reference environment

Linux or WSL2 with **Python 3.13**. Unix permission bits and the `fcntl` advisory lock are used where
the platform provides them; Windows-native execution of `assistantd` is not a supported v1 target
(run the daemon inside WSL, which is the reference setup).

## Upgrade notes

- The schema is unchanged from 0.8.0 (migrations `0001`–`0015`), so upgrading from `v0.8.0` is a
  software update plus a verification, not a migration step.
- Every historical schema this project ever shipped upgrades forward. See
  [upgrade-to-v1.md](../upgrade-to-v1.md) for the exact procedure.
- A database written by a *newer* build is refused rather than opened: the binary that wrote a
  runtime is the binary that understands it. Database downgrades are not supported.

## Backup and recovery

`pw integrity check` audits the runtime read-only; `pw backup create|verify|inspect` produces and
checks one hashed archive; `pw backup restore --to DIR` stages a recovery into a new directory and
invalidates the authorization state it copied. The archive contains the database and the referenced
mail and page objects — never credentials, the browser profile, configuration or derived indexes.
The README's *Disaster recovery* section is the operator procedure.

## Known limitations

- The mobile web UI is **trusted LAN HTTP** in v1: it is not a public Internet service, and it
  depends on the same private-network boundary (socket peer, no forwarding headers) that it always
  has. There is no cloud relay, no VPN and no third-party login.
- **SMTP cannot guarantee exactly-once delivery.** A definite success is recorded as such, an
  interrupted conversation becomes `UNKNOWN`, and reconciliation or a person decides what happened.
  Offline Sent-mail reconciliation is a check, not a promise.
- **eHall pages change.** The certificate pipeline re-checks the page contract before typing
  anything and fails closed on a mismatch, so a harmless site redesign can stop an errand until the
  contract is reviewed — that is the intended direction of failure.
- An **eHall `UNKNOWN` outcome requires manual inspection**: the submission may or may not have
  happened, and the assistant will not guess.
- **Web watchers cover public, unauthenticated HTTPS pages only**: no login, no JavaScript
  rendering, no non-default ports, no redirects.
- **Knowledge search is local FTS5**, not a vector database: it finds words, not meanings, and it
  reports where a match came from so you can read the original.
- **Confirmed facts are not auto-filled anywhere.** Fact confirmation is a durable, auditable record
  of something you told the assistant; no form, draft or model context is populated from it.
- **Playbooks are non-executing references.** Promotion means "this build still understands the
  payload"; running one is not a capability that exists.
- **MCP is a local stdio server with a bounded surface**: four resources, two read tools, optional
  knowledge excerpts and optional task writes. It cannot approve or execute anything.
- **Backups exclude external credentials and the authenticated browser profile.** After a restore
  you re-supply the SMTP/IMAP passwords, the model key and the eHall login, and you re-pair each
  phone.
- Filesystem watcher acceleration (instant re-index on file change) is not implemented; freshness
  comes from periodic reconciliation with a bounded delay.

## Security and privacy boundaries

- Secrets live in the environment, never in configuration, a log line, an event or a backup.
- Model prompts carry bounded, explicitly untrusted content; personal knowledge is attached only
  when you ask for it (`--context-query`, or `mcp.expose_knowledge = true`).
- The MCP server is disabled by default and read-only when enabled; the mobile control plane is
  disabled by default and can approve an exact action but can never execute one.
- Runtime files this project creates are owner-only: directories `0700`, files `0600`, including
  backups and restored content. Existing files that are already loose are reported by
  `pw integrity check`, never silently rewritten.
- Every release test runs without network access, and the acceptance suite keeps the socket guard
  on while exercising the real stores, the real worker and the real approval chain.

# ADR-0017 — Provider-Independent Model Port and Structured Output Boundary

## Title

Application code depends on a provider-independent model port; provider APIs, credentials and
reasoning stay inside an adapter, and every model answer passes deterministic local validation
before anything uses it.

## Status

Accepted

## Context

Phase 4 needs a language model for exactly one reason: turning a person's unstructured words
into structured intent. That is a *reasoning* capability, and it is the first component in this
project whose output is neither deterministic nor verifiable by construction.

Two temptations have to be designed out before any interpreter exists:

- **letting the provider shape the architecture.** If application code imports an SDK, knows a
  base URL, or branches on a model name, then swapping providers becomes a rewrite and every
  provider quirk leaks into the core;
- **trusting model output.** A provider's structured-output mode is generated by a model, and
  a model — like any untrusted input — can be wrong, truncated, or manipulated by the text it
  was asked to read.

## Decision

1. Core and application code depend only on `ModelPort`.
2. DeepSeek API details exist only inside the adapter.
3. The model never owns durable state.
4. The model never writes SQLite directly.
5. The model never touches the filesystem directly.
6. The model never drives the scheduler, email, browser or eHall.
7. Phase 4A provides no tool calls.
8. Every model output is treated as untrusted input.
9. Structured output requires a local JSON parse **and** a local JSON Schema validation.
10. A provider's server-side structured-output guarantee never replaces local validation.
11. Reasoning / chain-of-thought never enters `ModelResponse`.
12. Reasoning is never persisted, printed or logged.
13. Prompts and model outputs are not persisted automatically in this phase.
14. API keys are never written to config, to the repository, or to logs.
15. The DeepSeek key is injected from the environment only.
16. Missing model configuration must not affect tasks, knowledge, planner, scheduler or daemon.
17. Model calls in this phase happen only from the explicit `pw model test` command, or later
    from the interpreter.
18. Provider HTTP and network failures map onto project errors.
19. The adapter never retries automatically.
20. An incomplete or truncated provider response is never treated as success.
21. Usage metadata may be returned, but it is never a business fact.
22. `ModelPort` is replaceable by another provider adapter in the future.
23. Phase 4A implements no conversation memory.
24. Phase 4A implements no agent loop.
25. Phase 4A executes no natural-language command.

Additional frozen details:

- **One operation.** `ModelPort.complete(request) -> ModelResponse`. There is no `stream`, no
  `tools`, no `embed`, no `vision` and no conversation handle. A capability that could take an
  action needs its own boundary, designed deliberately.
- **System guidance is not a message.** `ModelRequest.instructions` carries it; `ModelRole`
  knows only `user` and `assistant`.
- **Text only.** Messages hold non-blank text. Multimodal input is out of scope even where a
  provider supports it.
- **Reasoning effort is provider-neutral** (`none`, `low`, `high`, `max`); an adapter maps it to
  whatever its provider calls it. No provider alias (`minimal`, `medium`, `xhigh`) appears in
  the core vocabulary.
- **Output modes** are `text` and `json_schema`. A `json_schema` request must carry a
  `JsonSchemaOutput` whose name matches `^[A-Za-z0-9_-]{1,128}$` and whose schema is a JSON
  object; the structured service validates it as a Draft 2020-12 schema *before* the request is
  sent.
- **The request carries no identity.** No API key, base URL, provider model name, user id or
  personal identifier is part of `ModelRequest`.
- **`ModelResponse` cannot represent private data.** It holds `text`, `model`, an optional
  `response_id`, optional `usage`, an optional `provider` name and neutral `metadata`. There is
  no field for reasoning, raw payloads or headers, so they cannot leak through a `repr`, a log
  or an error message.
- **Usage is optional and never a business fact.** Missing usage is `None`; unparseable numbers
  become zero rather than failing a successful call.
- **The DeepSeek adapter uses the Responses API** (`POST /responses`, non-streaming, stateless)
  with `deepseek-flash` as the default model name. Legacy `/chat/completions` is not the
  default path, and the retired names `deepseek-chat` / `deepseek-reasoner` are not used.
- **Structured output is requested as** `text.format = {"type": "json_schema", "name": ...,
  "schema": ...}`; `json_object` is never a substitute. Plain text uses `{"type": "text"}`.
- **Output items are walked explicitly**: `reasoning` is parsed and discarded, `message`
  `output_text` parts are concatenated in order, and a `function_call` (or any unknown item
  type) is a protocol error because no tools were ever offered.
- **Response status is checked**: `completed` proceeds, `incomplete` raises
  `ModelResponseIncomplete`, `failed` maps onto a provider-neutral error, anything else is a
  protocol error.
- **Status mapping** is fixed: 400/422 → `ModelInvalidRequest`, 401 →
  `ModelAuthenticationError`, 402 → `ModelBillingError`, 429 → `ModelRateLimited`, 500 →
  `ModelTransientError`, 503 → `ModelUnavailable`, other non-2xx → a provider-neutral fallback.
- **Timeouts are finite and layered**: connect, read, write and pool timeouts are all set;
  configuration bounds the read timeout between 10 and 600 seconds.
- **Error text is bounded** (≤500 characters, whitespace-collapsed) and never contains the
  prompt, the full provider payload, headers or a credential.
- **`FakeModelAdapter` is a port implementation for tests**, not a provider: it queues
  responses and errors and records requests. `provider = "fake"` is rejected by the config
  parser, so a fake can never stand in for a real provider in production.
- **No new durable state**: no migration, no `model_requests` / `model_responses` /
  `conversations` tables. Audit of future agent work needs its own design.

## Alternatives Considered

- **Call DeepSeek directly from application services**: fastest to write, and it welds the
  product to one provider's SDK, error shapes and request format. Rejected.
- **Put the provider SDK in the domain layer**: the domain is where the project's vocabulary
  lives; it must not depend on an HTTP client. Rejected.
- **Trust the JSON the provider returns**: a server-side schema guarantee is generated by a
  model, and validation that lives in the provider cannot protect the code that consumes the
  value. Rejected; parse and validate locally.
- **Let the model call business services directly**: capability without a boundary is exactly
  the failure mode ADR-0006 exists to prevent. Rejected.
- **Put the API key in `config.toml`**: a configuration file is copied between machines, read
  by other tools and pasted into issues. Rejected; the key comes from the environment, and the
  strict config parser rejects an `api_key` key outright.
- **Persist chain-of-thought**: private reasoning is not a product artifact, and storing it
  would create a durable record nobody needs. Rejected; reasoning is discarded in the adapter.
- **Implement a tool loop now**: it multiplies the ways a model can change state before the
  read-only path has been validated once. Rejected for this phase.

## Consequences

- The interpreter (Phase 4B) can be written against `ModelPort` and tested entirely with
  `FakeModelAdapter`: no network, no key, no cost, deterministic.
- A second provider is an adapter plus a config value, not an architectural change.
- Structured answers are safe to consume: if `StructuredModel.complete_json` returns, the value
  satisfied the caller's schema under local validation.
- Costs: a request that fails mid-flight is reported rather than retried (the caller must decide
  whether paying twice is acceptable); the smoke test is the only live call in this phase; and
  every provider quirk has to be encoded in one file — deliberately.
